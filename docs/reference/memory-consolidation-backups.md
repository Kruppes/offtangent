# Consolidation backups

Before each scheduled or manually started consolidation task, the service backs up that task's **own context scope**. The backup contains only existing `MEMORY.md` and Markdown files in `wiki/` and `users/`. It does not include daily notes, database facts, other agents, or other scopes. If the scope contains no eligible files, no timestamped backup is published; the task can still start. If the eligible file list and checksums match the latest complete backup, that backup is reused without consuming a retention slot. A failed backup prevents that scope's task from starting; the result and consolidation log give a fixed failure code and the first eight characters of its scope hash. Failures also persist as tool-call records in dedicated consolidation sessions, not user sessions. A cleanup failure after a successful backup is reported separately and does not prevent the task or replace its outcome.

Backups live in `memory-consolidation-backups/<scope-hash>/<timestamp>/` immediately under the configured data directory, not inside any memory tree. Each timestamp is UTC; collisions get a numeric suffix. A directory ending in `.partial` is incomplete, never valid for restore, and is removed during the next cleanup for that scope. The backup requires a local data volume shared with the memory source. Known Linux network filesystem types (NFS, SMB/CIFS, 9p, Ceph, AFS, NCP) and FUSE are rejected. Unknown types and platform-specific filesystem codes are not proof of a local volume: verify the actual data mount before deployment. Local FUSE mounts are also rejected by this conservative check. Ensure there is enough free space for the writable Markdown in each selected scope.

Set `memoryConsolidation.backupRetention` in `settings.json` or through the settings API to an integer from 1 to 365. Default: **7 different complete backups per scope**, not seven days: multiple changes and runs in one day can evict an earlier version that day. Discover damage before the oldest useful backup is displaced; copy a needed backup elsewhere before further consolidation. Identical runs and empty scopes do not consume slots. A settings API update restarts the scheduler automatically; after editing the file by hand, restart the service (the scheduler does not watch that file). Invalid manually edited retention falls back to 7 with a warning. The settings UI does not expose this advanced value. Backups for removed or moved scopes are not automatically deleted.

## Manual restore

1. Disable consolidation scheduling, stop the service and wait for any running consolidation to finish **before** copying files. Do not deploy while an earlier consolidation task is active: a recovered task from an older version may lack a backup. Keep a separate copy of the current scope if you may need to undo the restore.
2. Identify the exact affected scope directory. From the configured data directory, its **relative path** starts with `memory/scoped-v1/…`, or `agents/<agent-id>/memory/scoped-v1/…`; include every intervening ID segment. Do not include a leading `/`, a trailing `/`, `./`, the data-directory prefix, or a newline. Compute the full partition name with `printf %s '<relative/path>' | sha256sum` (on macOS, `printf %s '<relative/path>' | shasum -a 256`). **Do not use `echo`**: it adds a newline and yields a different hash. Locate `memory-consolidation-backups/<full-64-character-hash>/` beneath the data directory. The first eight characters are the identifier shown in the run result and log. Select a completed timestamp directory (never `.partial`). No plaintext scope mapping file is stored: ID-like scope segments can still be user-defined or sensitive, while a hash and the exact command suffice when the scope is known.
3. Compare the chosen snapshot and the live scope first: `diff -rq memory-consolidation-backups/<hash>/<timestamp>/ <relative/path>/`. The output identifies changed and extra files, including files created after the backup; inspect extra files before deleting any of them. Only `MEMORY.md` and `.md` files in `wiki/` and `users/` are covered; do not treat daily notes or other files as snapshot contents. From the data directory, copy the entries that actually exist in the snapshot: `cp -p memory-consolidation-backups/<hash>/<timestamp>/MEMORY.md <relative/path>/MEMORY.md` and, when present, `cp -Rp memory-consolidation-backups/<hash>/<timestamp>/wiki/. <relative/path>/wiki/` (likewise for `users/.`). Create missing destination directories first. Compare each restored file with `cmp`, verify permissions, ownership, and scope identity. Copying never removes files that are absent from the snapshot: only remove explicitly reviewed extras.
4. Restart the service and re-enable scheduling only after validation. Reconcile database fact rows and the search index separately: neither is rolled back when files are copied. Inspect facts extracted or changed since the chosen backup; correct stale facts through the supported memory workflow and rebuild or refresh the index as appropriate before relying on search results.

## Limits

This is a file-level restore, not a database rollback or an automatic restore tool. Concurrent interactive writes are not coordinated with the synchronous multi-file copy: a backup can contain files from different moments or a file truncated mid-write. Prefer an idle scope for a manually initiated run. Snapshot publication uses an atomic rename and file syncing, but it is not a transactional journal across the memory tree.
