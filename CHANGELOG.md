# Changelog

Notable behavior changes. Newest first.

## Unreleased — feat/kimi-live-models

### Kimi Code: live model list from `/coding/v1/models`

- `kimi-coding-oauth` and `kimi-coding` (preset flag `liveModels: 'kimi-coding'`) read `GET {region}/coding/v1/models` with the provider's own credential. The token comes only from `getApiKeyForProvider` (locked OAuth refresh); there is no separate refresh path. Triggers: once after start (deferred services), every 6 h, after create/save/sign-in of the provider, and when the Add Model dialog opens (plus a *Refresh model list from provider* button there).
- New ids go into `knownModels` and are enabled with the same rule as `syncNewCatalogModels` (appended to `enabledModels`; first run without `knownModels` only records the baseline). Vanished ids are logged once and kept everywhere.
- The answer is cached in `config/live-models.json` (next to `providers.json`). `buildModel()` precedence: for a catalog id (e.g. `k3`) the pi-ai catalog entry is used and a `provider.models` entry for it is ignored (unchanged existing behaviour; only the wire fields `thinkingLevelMap`/`compat` of the built-in override table apply); for a non-catalog id a `provider.models` entry wins over the live data. Live-only models inherit the wire contract of catalog `k3`, price 0.
- Thinking-only models (`supports_thinking_type: "only"`, documented ids `k3.1-pro*`) always get `thinkingLevelMap.off = null`, from every source, so `thinking=off` sends no `thinking` field instead of `{type: "disabled"}` (HTTP 400 on K3.1 Pro).
- A failed refresh logs one line and changes nothing. `kimi` (Moonshot API) is unchanged (catalog only).
- **OAuth refresh, all OAuth types (review fix):** a refresh token is presented at most once per process, keyed by its SHA-256 across all provider entries, not only per provider id. Two entries holding the same stored credential (duplicate provider, same account added twice) used to present the same rotating refresh token twice in parallel, which revokes the token family. Now the second caller joins the running refresh; the successor is written into every other entry that still holds the consumed token (synchronous load-compare-save), and an entry that already holds it is not rewritten. An adopted successor that already expired is refreshed with its own refresh token.
- **OAuth refresh, review round 2:** the per-token lock and the hand-over are bound to the issuer (provider type plus effective base URL / Kimi region, then the token hash). The same token string at another issuer is never joined or handed over, so an `anthropic-oauth` and an `openai-codex` entry with an identical refresh token can no longer receive each other's credentials. The successor is handed only to entries whose stored credential is exactly the one presented (access, refresh and expiry); an entry with a newer access token (non-rotating issuer) or another expiry is left alone. Every hop of the refresh chain redacts its error against every credential presented so far (message, stack and cause chain), so a rotated successor token cannot leak through a joined caller. `refresh()` has a hard 30 s deadline raced in-process (`OAUTH_REFRESH_TIMEOUT_MS`); an issuer that ignores the abort signal no longer blocks waiters or leaks lock entries. Single sign-ins (one entry per refresh token) are unchanged: one presentation of the stored credential, one write, no other entry touched.
- **Residual risk (documented, not solvable client-side):** when the deadline or a network error hits after the issuer already rotated the token server-side, the successor is lost and the stored, consumed refresh token is presented on the next attempt; the issuer may then reject it and ask for a new sign-in (*Renew token*).
- **Stale answers (review fix):** a live list request is bound to its source (type, auth method, effective base URL/region, credential generation: hash of the stored key or OAuth sign-in generation). Before anything is written the source is compared again; an answer for an old type/region/key/sign-in is discarded (no `knownModels`/`enabledModels`/cache change). A refresh after a key/region/sign-in change starts a new request instead of joining the running old one. Reading `providers.json` failures are one warning, never a rejected promise.
- **Residual risk (not changed):** `saveProviders` writes `providers.json` in place, without a cross-process lock. The deployment runs one Node process (`node dist/server.js`; tasks run in-process), and every load-modify-save on this path is synchronous, so writes cannot interleave inside it. A second process writing `providers.json` at the same time (e.g. a manual script) is not serialized.

## Unreleased — fix/image-only-voice-coalesce

### Photos without text always reach the model; photos + voice note become one turn

- **Bug fixed:** the Android app leaves out `content` when it is empty (kotlinx `encodeDefaults = false`), so the `skipSave` frame of photos sent without text had no `content`. `ws-chat.ts` died in `parsed.content.startsWith('/')` (unhandled rejection): no turn, no `message_ack`, no error frame. The frame now defaults `content` to `''`, and a frame that throws answers with an `error` frame instead of vanishing.
- **New hold (intentional behavior change):** a web/app message with attachments but no text waits up to 8 s (`TurnRunnerOptions.attachmentOnlyHoldMs`, `DEFAULT_ATTACHMENT_ONLY_HOLD_MS`) for a follow-up in the same strand. A follow-up inside the window (typically the voice note) takes the photos into ITS turn; without one the photos start their own turn after 8 s. A strand `/stop` drops a held message.
- **Carry-over:** a turn that starts now also gets the images of earlier user messages of the same strand that no turn answered yet (after the last assistant row, max. 10 min old; images only, recordings/documents are represented by their text).
- Not changed: Telegram (photos already start a turn with caption or file name as text; photo and voice note stay two turns). Voice note first, photos while that turn runs: the photos still get a queued turn of their own.
- **Review follow-up (images get at most one turn):** a stop or `/kill` during the hold stamps the user row `metadata.imagesDiscarded`; a turn that starts or is queued with images stamps their rows `metadata.imagesTakenBy = <turnId>`. The carry-over skips both, so images of a stopped hold, or of a turn that was stopped, killed or failed without an assistant row, never come back in a later turn. Carry-over is limited to rows of the same `user_id` (legacy `NULL` rows tolerated) and to the 8 newest images.
- Only messages whose attachments are ALL images are held; a document or a recording without text starts its turn at once.
- `message_ack` of a held message carries the additive fields `held: true` and `holdMs` (other acks unchanged; clients that do not know them ignore them). A throwing frame is logged with `errorClass(err)`.
- **Known limitation:** the hold lives in memory only. A server restart inside the 8-s window leaves that photo message without a turn. It is not lost: the row stays unstamped, so the next message in the strand within 10 min takes its images along. No start-up sweep: at boot nobody can tell a lost hold from a row the user deliberately left, and an unsolicited turn after a restart would race the existing restart recovery and could answer twice.

## Unreleased — feat/eco-context-policy

### Context-overflow guard for every request (Normal and Eco) — intentional behavior change

One shared pre-send check (`packages/core/src/request-overflow-guard.ts`, wired once in `buildStreamFn`, used by interactive strands and background tasks alike). Details: [docs/guide/models.md → Context-overflow guard](docs/guide/models.md).

What changes for requests that were previously sent:

- **Refused before sending (new):** when both input estimates (chars/3 safety estimate and the SDK's own measured-usage + chars/4 estimate) exceed the operative window (declared, or lower learned), the turn ends with a typed `[context-guard]` message instead of an HTTP 400 from the provider. Also refused: a learned window that could only be met by changing the thinking budget (the guard never changes reasoning fields).
- **Changed on the wire (new):** only when a provider has reported a smaller window than declared, the SDK's own `max_tokens` clamp runs against the learned window (the model copy passed to the SDK has `contextWindow` = learned value). Only `max_tokens` differs; history, system prompt, tool schemas, model id and thinking fields are identical.
- **One transparent retry (new):** a provider overflow error is retried at most once inside the same model call, before any event was forwarded (no tool re-runs, no history change). A second overflow fails fast with a typed, non-retryable message.
- **Persistence (new file):** learned windows are stored in `<DATA_DIR>/config/observed-context-limits.json` (lower-only, 7-day expiry).
- **Trusted learning only:** a window is learned only from a genuine provider overflow: HTTP 400/413 with a JSON error body, the provider's own `message` matching an anchored known grammar (OpenAI/vLLM, llama.cpp typed `n_ctx`, Anthropic), an overflow in the expected direction and an integer window of 1024–16,777,216 tokens. Echoed/validation text, 429/5xx, plain text and nonsense values never change the shared window; the original provider error is passed through.
- **Privacy:** the file stores only a fixed source label (e.g. `openai:max-context-length`), never upstream text, prompts or URLs; older (version 1) files are sanitized on load.

Unchanged: every request with no learned limit and not refused is passed to the SDK with the very same objects (wire byte-identical); ordinary provider errors pass through unmasked; Eco projection and busy toggles are not involved. Not covered: native adapters outside `buildStreamFn`.
